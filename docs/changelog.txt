2026-09-04  —  Per-phase cold-start settling (real fix, not just jitter reduction)
-----------------------------------------------------------------------------------
  Change:  A fresh DSLogic capture of profile 3 (90% -> 10% ramp) exposed
        that the previous two entries below, while a real improvement,
        hadn't actually gotten the phase-lock settling right -- they
        eliminated the catastrophic U/V/W collision, but connected all
        three outputs together after waiting for a single event (one
        full Master period). Since V/W's own ResetTrigger (MASTER_CMP1/
        CMP2) fires much earlier (1/3, 2/3 of a period), by the time all
        three connected together V/W were already mid-way through
        whatever their comparators had been doing since that earlier,
        still-hidden reset -- exposing a stale/in-progress duty cycle,
        not a clean pulse, and what looked like a "recovery" edge near
        120/240 deg was actually just each timer's own natural TIMPER
        rollover after its hidden reset -- which only lands near there
        by coincidence of that particular duty value, not by design.
        Confirmed by decoding the .dsl capture's raw per-channel data
        directly (per-channel bit-packed L-N/0 files inside the archive).

        Real fix: HRTIM1_PWM_Start() now waits for and connects each
        phase SEPARATELY, at its own reset-trigger event -- new static
        helper HRTIM1_WaitForPhaseAndConnect(), called three times (V at
        MASTER_CMP1, W at MASTER_CMP2, U at MASTER_PER/MREP, in that
        chronological order within one masked critical section). V/W
        additionally re-force output1 ACTIVE/output2 INACTIVE (direct
        SETx1R/RSTx2R writes, same reasoning as the direct OENR write)
        at the exact moment their flag is observed -- necessary because
        an externally-triggered counter reset does NOT itself generate
        a fresh SET event (confirmed against the capture data), so
        without this the output would still reflect whatever the
        original pre-counter-start force-ACTIVE call left it in, not a
        clean restart. Timer A needs no such re-force: MASTER_PER
        coincides with its own natural rollover, a genuine TIMPER
        SET-source event that already transitions the output correctly
        on its own. Net effect: nothing visible on V/W until 120/240 deg
        after U's first edge, then a clean, correctly-timed,
        correctly-dutied pulse -- not a snapshot of an in-progress cycle.

        Considered and rejected: reverting to relying solely on
        pre-loading step 0's per/compare values (raised directly, in
        chat) instead of delaying output connection at all. Doesn't
        work -- PFM_Restart() already pre-loads those values via
        PFM_ApplyCurrentStep()/HRTIM1_SoftwareUpdate() BEFORE
        HRTIM1_PWM_Start() runs, unchanged since before any of these
        fixes existed, and the original bug happened anyway with that
        pre-loading already in place. The defect was never stale
        register content; it's genuine counter-timing settling that
        only resolves once real time has elapsed, which register values
        can't substitute for.

        Verified: full clean rebuild, zero warnings (text 34904->35036
        bytes vs. the masked-interrupt entry below). Reflashed, table
        re-uploaded, FIRE -> OK twice back to back, board stayed fully
        responsive to *IDN?/TABLE? throughout.

        CONFIRMED on real hardware the same day: a ~5 ms DSLogic capture
        spanning nearly the entire shot (499 of 500 periods) shows
        phase spacing holding rock-solid at ~3300 ns/~6600-6700 ns
        (target 3333/6667 ns for 120/240 deg) consistently from the
        cold-start edge all the way to the last period, and U's duty
        tracking profile 3's 90% -> 10% ramp cleanly throughout (86% ->
        73% -> 56% -> 41% -> 24% -> exactly 10.0% on the final sampled
        period) -- confirms PFM_CycleBoundaryHandler() advancing the
        table stays correctly phase-locked for the whole shot, not just
        at the exact startup instant. This closes out the cold-start
        phase-lock investigation that started with the first DSLogic
        capture earlier today.

2026-09-04  —  Masked interrupts during the settling wait's critical section
---------------------------------------------------------------------------
  Change:  Second follow-up to the cold-start phase-lock fix. A fresh
        DSLogic capture after the loop-tightening entry directly below
        showed real improvement (first pulse 200 ns -> 600 ns; U/V/W
        edge-timing error ~700 ns -> ~230-270 ns off target) but a
        genuine, non-shrinking residual remained -- and it varied run
        to run (200 ns, then 600 ns), which pointed away from a fixed
        software-latency floor and toward interrupt preemption:
        HRTIM1_PWM_Start()'s poll runs with global interrupts enabled,
        and SysTick (priority 0, the HIGHEST in this firmware -- see
        FixSysTickPriority()) or USART2 (priority 2, this very FIRE
        command's own reply path) can legitimately preempt the tight
        poll loop for a handful of cycles at exactly the wrong moment.

        Fix: wrapped the poll and the OENR write in __disable_irq()/
        __enable_irq() -- a short, bounded critical section (worst case
        ~385 us for a uint16_t `per`'s longest representable period,
        typically ~10 us at 100 kHz). Since HAL_GetTick() can't advance
        while global interrupts are masked (it's SysTick-driven, and
        SysTick is masked too), the previous entry's wall-clock timeout
        doesn't work here -- replaced with a plain 1,000,000-iteration
        spin-count ceiling, deliberately loose (many milliseconds of
        real time even pessimistically) rather than tuned, so it can
        only ever trip on a genuine hang, never in normal operation.

        Verified: full clean rebuild, zero warnings. Reflashed, table
        re-uploaded, FIRE -> OK repeatedly (fired twice back to back),
        board stayed fully responsive to *IDN?/TABLE? throughout -- no
        hang, and no UART data loss from the masked window (a ~10 us,
        worst-case ~385 us mask is far shorter than the ~1 ms/byte
        margin at 9600 baud, so an in-flight RX byte just sits in the
        UART's hardware data register a little longer, unaffected).
        Re-capturing with DSLogic to confirm the residual actually
        shrank is the next step, not yet done as of this writing.

2026-09-04  —  Tightened the cold-start settling wait's reaction latency
--------------------------------------------------------------------------
  Change:  Follow-up to the cold-start phase-lock fix directly below,
        after a fresh DSLogic capture confirmed it worked (U/V/W
        genuinely staggered, ~120/240 deg spacing accurate to a few
        counts in steady state) but also showed a small residual: the
        very first visible pulse still read ~200 ns instead of the
        clean ~1000 ns steady-state width -- software reaction latency
        between the MREP flag actually going true in hardware and
        HRTIM1_PWM_Start() acting on it, not a phase-lock problem.

        Two changes to HRTIM1_PWM_Start(), same function, no new
        approach:
          - The polling loop's inner spin no longer calls HAL_GetTick()
            on every iteration -- that's a real function call, added
            avoidable cycles to the exact latency being chased. The
            wall-clock timeout (still 5 ms, still Error_Handler() on
            expiry) is now sampled only every 256 spins; the inner loop
            itself is just a register read, compare, and branch.
          - Connecting the outputs on flag-observed now writes OENR
            directly (hhrtim1.Instance->sCommonRegs.OENR |= outputMask)
            instead of calling HAL_HRTIM_WaveformOutputStart(), which
            does the identical single register write wrapped in
            __HAL_LOCK/State=BUSY/__HAL_UNLOCK bookkeeping this call
            site doesn't need. Same precedent already used by
            HRTIM1_SoftwareUpdate()'s direct CR2 write elsewhere in
            this file. Re-arming HRTIM_MASTER_IT_MREP (needed before
            this function returns, not before) now happens AFTER the
            OENR write, not before -- it isn't time-critical, and
            keeping it out of the way removes two more register
            round-trips from the critical path.

        Verified: full clean rebuild, zero warnings (text +16 bytes net
        vs. the previous entry). Reflashed over serial, re-uploaded the
        table, FIRE -> OK promptly, board stayed responsive to *IDN?
        afterward -- the tightened spin loop and reordering introduced
        no hang or regression. Re-capturing with DSLogic to confirm the
        first-pulse width actually improved is the next step, not yet
        done as of this writing.

2026-09-04  —  Bugfix: cold-start phase-lock glitch on every FIRE
------------------------------------------------------------------
  Change:  Found via a real DSLogic U3Pro32 capture (decoded by hand --
        no capture-analysis tooling in this repo, just the .dsl
        archive's raw bit-packed channel data). Symptom: on every
        `FIRE`, U/V/W's first-ever output edges all landed on the
        exact same sample -- not staggered 120°/240° apart as
        intended -- producing ~1-2 garbled cycles (one phase measured
        holding ON ~7.4x too long; that first "period" reading as low
        as ~60 kHz) before self-correcting from cycle 2 onward. Matches
        what the user had independently noticed as "~60 kHz garbage for
        the first ~2 periods" on a real scope.

        Root cause: HRTIM1_PWM_Start()'s HAL_HRTIM_WaveformSetOutputLevel()
        calls (needed, per ST's own HAL guidance, to avoid an undefined
        complementary-pair state when DeadTimeInsertion is enabled)
        force TA1/TB1/TC1 all ACTIVE at the same instant, with no
        regard for their intended stagger. Timer A's ResetTrigger
        (MASTER_PER) happens to coincide with its own natural period
        rollover, but Timers B/C (ResetTrigger = MASTER_CMP1/CMP2)
        aren't genuinely phase-locked until they've received their
        first Master-CMPx-triggered reset -- which hasn't happened yet
        at the moment the counters first start.

        Fix: HRTIM1_PWM_Start() now starts the counters as before, but
        delays connecting the outputs to the pins (WaveformOutputStart())
        until the Master's own MREP (repetition) flag confirms one full
        period has genuinely elapsed in hardware -- by then every
        timer has already received its first phase-defining reset, so
        the first VISIBLE edge is already correctly phase-locked.
        Waiting on the hardware flag rather than computing a busy-wait
        from `per`/HRTIM_TIMER_CLK_HZ makes this automatically correct
        for whatever period is currently loaded -- no hardcoded 100 kHz
        assumption, so it stays correct if/when variable-frequency
        tables exist (per user request, 2026-09-04). HRTIM_MASTER_IT_MREP
        (armed at boot by HRTIM1_EnableMasterInterrupt(), and still
        armed from any previous shot) is masked for the duration of
        this wait and any stale flag discarded first -- otherwise
        PFM_CycleBoundaryHandler() would fire for real during the
        settling wait and silently advance the table to step 1 before
        step 0 was ever visible on the pins. Bounded to 5 ms
        (>12x margin over the ~385 us worst-case period a uint16_t
        `per` can represent) with an Error_Handler() fallback, matching
        this file's existing defensive-timeout convention (see
        HAL_HRTIM_PollForDLLCalibration() in HRTIM1_FullInit()).

        Verified: full clean rebuild (make clean && make all -j4, zero
        warnings; text grew 88 bytes). Verified on real hardware:
        reflashed over serial, re-uploaded a 500-entry table, sent
        FIRE -> OK promptly (no hang from the new bounded poll -- the
        real risk this change introduced), board stayed responsive to
        *IDN? immediately after. Re-capturing with DSLogic to confirm
        the actual edge timing is now clean is the next step, not yet
        done as of this writing.

2026-09-04  —  Bugfix: pfm_table_upload.py ~25-50x slower than it
                should have been
------------------------------------------------------------------
  Change:  Found while running the first real end-to-end bench pass
        (flash -> upload -> FIRE) of the FIRE command below.
        send_and_expect_ok() read replies with a manual
        `while time.time() < deadline: chunk = ser.read(128)` poll
        loop against a Serial(..., timeout=1.0) port. pyserial's
        read(size) keeps trying to fill the *entire* requested size
        until the port's own timeout elapses, even once a short reply
        (every firmware reply here is a handful of bytes, e.g.
        "OK\r\n") has already fully arrived -- so every single
        TABLE:STEP round-trip was costing close to the full 1 s
        timeout instead of the real ~20-30 ms wire time at 9600 baud.
        500 entries were taking 8+ minutes; this was mistakable for
        "9600 baud is just slow", but the baud rate was never the
        problem.

        Fix: replaced the poll loop with ser.read_until(b"\n"), which
        returns the instant the terminator arrives (falling back to
        the port's timeout only on a genuine no-reply failure, which
        still needs to time out and raise). No protocol or firmware
        change. Verified: a real 500-entry upload (profile 1) dropped
        from 500-1000+ s to 20.2 s measured wall-clock, same successful
        `TABLE:END -> OK 500` result.

        Considered and deferred (see the FIRE entry below's own
        real-hardware pass for why 20 s was accepted as fine for now):
        batching multiple TABLE:STEP entries per line (needs a
        firmware/protocol change; marginal win once the read-loop bug
        is fixed, since ~30 s of raw payload at 9600 baud is close to
        the real floor for 500 entries either way) and pipelining
        without waiting for each ACK (real risk of silently overrunning
        uart.c's single-line RX buffer without first checking its
        buffering model -- not done without that check).

2026-08-31  —  Bugfix: ROM bootloader Go-jump left interrupts dead
---------------------------------------------------------------------
  Change:  Found and fixed on real hardware while first testing
        wham_serial_flash.py end-to-end. Root cause, symptom, and fix
        are documented in full in boot_jump.c's BootJump_CheckAndEnter()
        and in docs/serial_reflash_guide.md Section 4 -- summary:

        Symptom: a serial reflash reported success (write + verify both
        passed via stm32flash), but the newly-flashed firmware was
        completely unresponsive over USART2 afterward -- *IDN? got no
        reply -- until the board was power-cycled, at which point it
        worked immediately and correctly.

        Root cause: stm32flash's -g (the ROM bootloader's "Go" command)
        branches to the new app without performing a real chip reset.
        SCB->VTOR and SYSCFG->MEMRMP, left pointing at the ROM
        bootloader's own vector table from the *previous* boot's jump
        INTO the bootloader (the normal BOOT-command flow), are never
        corrected by anything in this firmware -- system_stm32g4xx.c's
        SystemInit() only sets VTOR under USER_VECT_TAB_ADDRESS, which
        is not defined here (the CubeMX default). Every interrupt,
        including the USART2 RX interrupt the whole command parser
        depends on, vectored into the ROM bootloader's table instead of
        the app's own.

        Fix: BootJump_CheckAndEnter()'s normal-boot path now
        unconditionally restores SCB->VTOR = FLASH_BASE and the main-
        Flash SYSCFG remap before falling through to HAL_Init(). No-op
        on a true reset (both already correct there); the actual fix on
        the Go-jump path.

        Verified: flashed a new firmware version over serial, queried
        *IDN? immediately with no manual reset, got the new version back
        correctly -- confirmed twice in a row (v0.5, then v0.6).

        Not yet ported to the sibling PFM-STM32G474/-V4 projects, which
        carry the same unfixed boot_jump.c this one was forked from --
        deliberately deferred per project decision, not forgotten.

2026-08-31  —  SCPI-style hierarchical command dispatch
-------------------------------------------------------------
  Change:  Replaced cmd_parser.c's flat case-sensitive exact-match table
        with SCPI-style matching (scpi_match()/scpi_token_match()):
        colon-separated hierarchy levels, per-level short/long form
        (mandatory-uppercase-prefix + optional-lowercase-suffix),
        case-insensitive, exact query-suffix (?) matching, tolerant of
        a leading colon on input. Table stays flat (one row per leaf
        command, full mnemonic path as the pattern) -- no separate tree
        structure to build or maintain.

        Verified with a standalone native (non-cross-compiled) test
        harness before wiring in: 19 cases covering short/long form,
        mixed-form, wrong depth, wrong query suffix, case variants, and
        leading-colon tolerance, all passing. Also confirmed strtok_r/
        strncasecmp/isupper actually link under this toolchain's
        --specs=nano.specs (not guaranteed in every newlib-nano config).

        *IDN was renamed to *IDN? to match real IEEE 488.2/SCPI form,
        now that the trailing ? is meaningfully enforced.
